# Веб-сервис бронирования ресурсов «Бронь без конфликтов»

## 1. Назначение, стек и вид ресурсов

* **Назначение сервиса:** Обеспечение прозрачного и безопасного бронирования ресурсов образовательного учреждения без пересечений по времени, с разграничением ролей пользователей, защитой от повторных запросов и целостностью данных.
* **Вид ресурсов:** Переговорные комнаты (в единицу времени единица ресурса бронируется целиком).
* **Пользователи:** Обычные пользователи (студенты/преподаватели) и Администраторы.
* **Технологический стек:**
  * **Бэкенд:** Node.js, Express.js
  * **База данных:** PostgreSQL
  * **Безопасность и JWT:** `jsonwebtoken`, `bcryptjs`
  * **Фронтенд:** HTML, CSS, JavaScript
  * **CI/CD:** GitHub Actions

## 2. Бизнес-правила, логика времени и разграничение доступа

### Правила времени и отмены
1. **Режим работы:** Ресурсы доступны ежедневно с 08:00 до 22:00 по московскому времени (Europe/Moscow, UTC+3).
2. **Шаг и длительность:** Шаг выбора времени — 30 минут. Длительность одной брони — от 30 минут до 4 часов.
3. **Ограничения дат:** Бронирование целиком помещается в один рабочий день; время окончания строго позже начала. Начало не может находиться в прошлом и доступно не позднее чем через 30 суток от текущего момента (проверка выполняется по серверному времени).
4. **Пересечение интервалов:** Интервал имеет вид `[начало, окончание)`. Момент окончания считается свободным для следующего бронирования. Конфликт возникает, когда начало новой записи раньше окончания существующей И окончание новой позже начала существующей.
5. **Отмена:** 
   * До начала записи пользователь может отменить только свою будущую бронь.
   * Администратор может отменить любую будущую запись с обязательным указанием причины отмены.
   * Начавшиеся и завершенные записи отменять запрещено. Повторная отмена не создает нового изменения состояния.

### Правила авторизации и прав доступа
1. Владелец создаваемой записи и его роль определяются строго на сервере по расшифрованному и проверенному JWT-токену из заголовка `Authorization: Bearer <token>`. Переданные клиентом параметры не влияют на права.
2. При попытке обычного пользователя запросить чужую запись сервер возвращает статус **404 Not Found**, скрывая существование и данные чужого объекта.
3. При обращении обычного пользователя к административным маршрутам сервер возвращает **403 Forbidden**. Защита действует на уровне API независимо от состояния кнопок в интерфейсе.

## 3. Схема базы данных (СУБД PostgreSQL)

### Таблицы и ограничения

1. **`users` (Пользователи)**
   * `id` (UUID, Primary Key, по умолчанию `gen_random_uuid()`)
   * `name` (VARCHAR(100), NOT NULL, от 2 до 100 символов)
   * `login` (VARCHAR(64), UNIQUE, NOT NULL, от 3 до 64 символов)
   * `password_hash` (VARCHAR(255), NOT NULL, хеш bcrypt)
   * `role` (VARCHAR(20), CHECK IN ('пользователь', 'администратор'))

2. **`resources` (Ресурсы / Переговорные)**
   * `id` (UUID, Primary Key)
   * `name` (VARCHAR(120), NOT NULL)
   * `description` (VARCHAR(1000), DEFAULT '')
   * `location` (VARCHAR(200), NOT NULL)
   * `is_active` (BOOLEAN, DEFAULT TRUE)

3. **`bookings` (Бронирования)**
   * `id` (UUID, Primary Key)
   * `resource_id` (UUID, Foreign Key -> `resources.id`)
   * `owner_id` (UUID, Foreign Key -> `users.id`)
   * `start_time` (TIMESTAMP, NOT NULL)
   * `end_time` (TIMESTAMP, NOT NULL, CHECK `end_time > start_time`)
   * `purpose` (VARCHAR(300), NOT NULL, длина от 5 до 300 символов)
   * `status` (VARCHAR(20), DEFAULT 'Активно', CHECK IN ('Активно', 'Отменено'))
   * `created_at` (TIMESTAMP, DEFAULT UTC)
   * `cancelled_at` (TIMESTAMP NULL)
   * `cancelled_by` (UUID NULL, Foreign Key -> `users.id`)
   * `cancel_reason` (VARCHAR(300) NULL)
   * **Ограничение исключения пересечений (GiST EXCLUDE):**
     `EXCLUDE USING gist (resource_id WITH =, tsrange(start_time, end_time) WITH &&) WHERE (status = 'Активно')`

4. **`idempotency_keys` (Ключи повторных запросов)**
   * `id` (UUID, Primary Key)
   * `user_id` (UUID, Foreign Key -> `users.id`)
   * `key` (VARCHAR(128), NOT NULL, от 8 до 128 символов)
   * `request_fingerprint` (VARCHAR(64), NOT NULL)
   * `booking_id` (UUID, Foreign Key -> `bookings.id`)
   * `created_at` (TIMESTAMP, DEFAULT UTC)
   * **Ограничение:** `UNIQUE(user_id, key)`

5. **`audit_logs` (Аудит действий)**
   * `id` (UUID, Primary Key)
   * `created_at` (TIMESTAMP, DEFAULT UTC)
   * `actor_id` (UUID NULL -> `users.id`)
   * `action` (VARCHAR(80), NOT NULL)
   * `object_type` (VARCHAR(40), NOT NULL)
   * `object_id` (UUID NULL)
   * `result` (VARCHAR(20), CHECK IN ('успех', 'отказ'))
   * `request_id` (VARCHAR(64), NOT NULL)

### Индексы
* `idx_bookings_owner_start` (`owner_id`, `start_time DESC`) — оптимизирует выборку личных записей пользователя (`GET /api/bookings/my`).
* `idx_bookings_resource_active_interval` (`resource_id`, `start_time`, `end_time`) WHERE `status = 'Активно'` — ускоряет поиск занятых интервалов при открытии карточки ресурса.
* `idx_audit_logs_created_at` (`created_at DESC`) — ускоряет построение ленты аудита для администратора.

## 4. Объяснение защиты от конкуренции и повторных запросов

### Защита от параллельных бронирований (Race Conditions)
Для предотвращения состояния гонки (когда два параллельных запроса одновременно видят свободный интервал и создают пересекающиеся записи) применен **гибридный двухуровневый механизм**:
1. **Уровень изоляции и явных блокировок в транзакции:** При создании бронирования транзакция выполняет `SELECT id, is_active FROM resources WHERE id = $1 FOR UPDATE`. Это блокирует строку ресурса в БД, выстраивая конкурентные запросы на один ресурс в строгую очередь. Операция отключения ресурса админом запрашивает блокировку в аналогичном порядке.
2. **Ограничение цельности на уровне СУБД (PostgreSQL EXCLUDE Constraint):** На таблицу `bookings` наложено ограничение `bookings_no_overlap` с использованием пространственного индекса `GiST` на диапазон `tsrange(start_time, end_time)`. Даже если приложение будет развернуто в нескольких экземплярах (кластер из множества Node.js серверов), СУБД гарантирует атомарность и физически отвергнет любую попытку создания пересекающихся активных интервалов с ошибкой сериализации/уникальности (`23P01`). Конфликт преобразуется в понятный клиенту ответ **409 Conflict** с сообщением: *«Ресурс уже занят в выбранное время»*.

### Защита от повторных отправка и сбоев сети (Идемпотентность)
1. Клиент передает случайный уникальный ключ в заголовке `Idempotency-Key` (длина 8–128 символов).
2. На сервере рассчитывается `request_fingerprint` (SHA-256 хэш нормализованных параметров: `resourceId`, `startTime`, `endTime`, `purpose`).
3. В рамках единой транзакции создаются запись бронирования и запись ключа в таблице `idempotency_keys`. Уникальность `(user_id, key)` обеспечивается БД.
4. **Поведение при повторе:**
   * Повтор запроса с тем же `Idempotency-Key` и теми же данными возвращает ранее созданную запись с кодом **200 OK** без повторной вставки.
   * Использование ранее использованного ключа с изменившимися данными возвращает **409 Conflict** (*«Ключ повторного запроса уже использован с другими данными»*).


## 5. Описание REST API

Все ответы с ошибками имеют стандартную структуру: `{ "code": "STRING", "message": "STRING", "traceId": "UUID" }`.

| Метод | Маршрут | Права | Назначение и коды ответов |
|---|---|---|---|
| `POST` | `/api/auth/register` | Публичный | Регистрация (`201`, `400`, `409`) |
| `POST` | `/api/auth/login` | Публичный | Вход, получение JWT (`200`, `400`, `401`) |
| `GET` | `/api/resources` | JWT | Каталог активных ресурсов, поиск `?search=` (`200`, `401`) |
| `GET` | `/api/resources/:id/availability` | JWT | Занятые интервалы даты `?date=YYYY-MM-DD` (`200`, `400`, `404`) |
| `POST` | `/api/bookings` | JWT | Создание записи. Требует `Idempotency-Key` (`201`, `200` replayed, `400`, `401`, `409`) |
| `GET` | `/api/bookings/my` | JWT | Просмотр личных записей пользователя (`200`, `401`) |
| `POST` | `/api/bookings/:id/cancel` | JWT / Admin | Отмена будущей записи (для админа с причиной) (`200`, `400`, `401`, `404`, `409`) |
| `GET` | `/api/admin/bookings` | Администратор | Просмотр всех записей с владельцами и целями (`200`, `401`, `403`) |
| `GET` | `/api/admin/audit` | Администратор | Просмотр журнала аудита действий (`200`, `401`, `403`) |
| `GET` | `/health/live` | Публичный | Проверка жизнеспособности процесса Node.js (`200 UP`) |
| `GET` | `/health/ready` | Публичный | Проверка готовности сервиса и доступности БД (`200 READY` / `503 Service Unavailable`) |
